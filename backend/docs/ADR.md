# Architecture Decision Records

## ADR-001: FastAPI over Django REST Framework

**Status**: Accepted
**Date**: 2026-04-22

**Context**: The legacy system uses Django 4.2 with SQLite. The new system requires
async I/O (concurrent WebSocket connections, Celery task dispatching, asyncpg queries).
Django's ORM is synchronous by default; Django Channels adds async but requires
significant extra infrastructure.

**Decision**: Use FastAPI with async handlers throughout.

**Consequences**: All database access must use async SQLAlchemy sessions. No Django ORM,
Django admin, or Django middleware. Pydantic replaces Django serializers.

---

## ADR-002: SQLAlchemy 2.0 async over Django ORM or Tortoise ORM

**Status**: Accepted
**Date**: 2026-04-22

**Context**: We need an async-native ORM that works well with PostgreSQL and supports
complex joins, aggregates, and migrations.

**Decision**: SQLAlchemy 2.0 with `create_async_engine` and `AsyncSession`.
Alembic for migrations.

**Consequences**: All query code uses `await session.execute(select(...))` syntax.
Relationships are loaded explicitly (no lazy loading in async context). Alembic
migration scripts are autogenerated from model metadata.

---

## ADR-003: UUID v4 primary keys on all entities

**Status**: Accepted
**Date**: 2026-04-22

**Context**: Integer auto-increment PKs expose record counts and are enumerable via
sequential API calls (e.g. GET /students/1, /students/2).

**Decision**: All models use `UUID(as_uuid=True)` PK with `default=uuid.uuid4`.

**Consequences**: FKs are also UUID columns. JOIN performance is slightly lower than
integer PKs but acceptable at school-scale data volumes (<100k rows per table).
Legacy Django integer IDs are remapped to UUIDs during data migration (see MIGRATION_PLAN.md).

---

## ADR-004: HS256 JWT over RS256

**Status**: Accepted
**Date**: 2026-04-22

**Context**: JWT tokens are verified by a single FastAPI service.

**Decision**: HS256 (HMAC-SHA256) with a single shared `SECRET_KEY`.

**Consequences**: Simpler key management — one secret, not a keypair. If a second
service (e.g. a separate WebSocket service) needs to verify tokens independently,
migrate to RS256 (the Pydantic schema and jose calls are the only changes needed).

## ADR-005: Repository pattern between service and ORM

**Status**: Accepted
**Date**: 2026-04-22

**Context**: Without a data-access abstraction, business logic in services becomes
coupled to SQLAlchemy syntax, making unit tests require a real database.

**Decision**: Every model has a corresponding repository class that encapsulates
all SQLAlchemy queries. Services call repositories; endpoints call services.
Repositories are never called directly from endpoints.

**Consequences**: Unit tests can mock repositories. Integration tests test repositories
against a test database. The service layer remains pure Python with no ORM imports.

---

## ADR-006: Pydantic v2 for all request/response schemas

**Status**: Accepted
**Date**: 2026-04-22

**Context**: FastAPI's native integration with Pydantic provides automatic request
validation and OpenAPI doc generation at zero extra cost.

**Decision**: Pydantic v2 (`model_config = ConfigDict(from_attributes=True)`) for
all schemas. SQLAlchemy models are never returned directly from endpoints — always
converted to a Pydantic response schema first.

**Consequences**: Every model needs a corresponding `Create`, `Update`, and `Response`
schema in `app/schemas/`. The `from_attributes=True` config allows `model_validate(orm_obj)`.
